# Phase 01: Component Inventory And Microgame Metadata

Status: proposed.

## Goal

Add a typed framework model for small physical component constraints without
building a product submission workflow.

Competition designers often work under constraints such as one card, nine
cards, eighteen cards, a roll-and-write sheet, a mint-tin inventory, or a small
set of dice and tokens. The SDK should understand those constraints as game
metadata so agents, docs, scenario checks, and UI helpers can reason about them
consistently.

## In Scope

- Additive manifest or authoring metadata for component inventories.
- Typed component categories for:
  - Cards.
  - Dice.
  - Tokens/counters.
  - Tracks.
  - Sheets.
  - Boards/maps.
  - Common components supplied by players, such as coins or standard dice.
- Microgame profile metadata, such as `one-card`, `nine-card`, `eighteen-card`,
  `mint-tin`, `roll-and-write`, and `postcard`.
- Validation helpers that can assert authored seeds/components fit the declared
  inventory.
- Docs and examples showing how metadata informs tests and UI, not product
  submission.

## Out Of Scope

- BGG export formats.
- Public gallery submission fields.
- Uploading printable PDFs.
- Enforcing contest-specific legal rules.

## Likely Touchpoints

- `packages/sdk-types/src/contracts.ts`
- `packages/sdk/src/reducer/authoring/*`
- `packages/sdk/src/authoring/*`
- Generated metadata and export-surface tests.
- Reference-game manifests under `examples/reference-games/`.
- Docs generated by `scripts/generate-agent-reference.mjs` if public exports
  change.

## Design Requirements

- Metadata must be additive and tolerant-reader friendly.
- Component inventory should not duplicate existing card/resource/board state;
  it should describe physical constraints and intended component classes.
- Runtime game state should not be forced to mirror physical component
  inventory one-to-one. A one-card game may still have multiple logical marks,
  spaces, or state values.
- Agents should be able to ask "does this game fit an eighteen-card contest?"
  from metadata and tests.

## Acceptance Criteria

- At least one reference game declares a compact component inventory.
- A validation test fails when a fixture exceeds its declared physical
  component budget.
- Public docs explain the difference between physical component inventory and
  runtime state.
- Existing reference games continue to pass packed-consumer verification.

## Suggested Verification

```bash
pnpm typecheck
pnpm generate:check
pnpm publication:check
pnpm reference-games:check
pnpm reference-games:test:packed --required
```
